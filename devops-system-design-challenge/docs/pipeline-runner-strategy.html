Runner trade-offs per stage group

Dimension Stages 1–6 · ubuntu-latest Stages 7–12 · k8s-system-design
Architecture AMD64 (GitHub-hosted cloud) ARM64 (Raspberry Pi 4 / K3s)
Why this runner Downloads AMD64-only binaries (conftest_x86_64, kyverno_x86_64). Would break on ARM64. Must reach local network: 192.168.1.106:6443 and traefik.mykubernetes.com. Cloud runners can't reach these.
Cluster access ✗ Not needed — only checkout, scan, build, push to GHCR. ✓ Required — kubectl set image, rollout status, healthz probe, cosign verify.
ARM64 compatible tools Irrelevant — AMD64 runner. ✓ All tools used here support ARM64: kubectl, cosign, curl.
Cost GitHub-hosted minutes (free tier: 2000 min/month for public repos). Free — runs on your own hardware.
Cold start Fast — GitHub spins up VM instantly. Near-zero — ARC scales runner pod from 0 on demand (~10s).
Blast radius if runner dies Low — GitHub handles infra, auto-retried. Medium — depends on Pi cluster health. If cluster is down, stages 7–12 block.
Parallel capacity Unlimited — GitHub scales runners. Max 3 runners (configured in ARC AutoscalingRunnerSet).
Binary download risk AMD64 binaries hardcoded — no risk on this runner. Only ARM64-native tools used — no binary download risk.

Why not run everything on one runner?

Option Problem
All on ubuntu-latest GitHub-hosted runners can't reach 192.168.1.x or traefik.mykubernetes.com. Stages 7–12 timeout on every kubectl/curl call.
All on k8s-system-design (ARM64) Conftest and Kyverno CLI binaries are downloaded as x86_64. Running them on ARM64 causes exec format error. Stages 4–5 break.
Split: 1–6 cloud / 7–12 local ✓ Best of both — AMD64 for compute/scan stages, ARM64/local for deploy stages that need cluster access.

ArgoCD + Argo Rollouts — inside or outside the pipeline?

Aspect Current approach (kubectl set image) With ArgoCD + Argo Rollouts
Deploy mechanism Pipeline runs kubectl set image imperatively. Pipeline updates image tag in Git (Kustomize/Helm values). ArgoCD detects the diff and syncs declaratively.
Who lives inside the pipeline? Stages 7, 8, 12 — full deploy logic in YAML. INSIDE Stage 6 pushes image + updates GitOps repo with new tag. Optionally: argocd app sync + wait for health.
Who lives outside the pipeline? Nothing — pipeline owns everything. OUTSIDE Deployment strategy (canary weights, analysis runs, rollback) is declared in the Rollout resource in Git — ArgoCD + Argo Rollouts executes it autonomously.
Progressive delivery Basic rollout with auto-rollback on rollout status timeout. Canary (10% → 50% → 100%), blue-green, with AnalysisRun checking Prometheus metrics before promoting.
Rollback kubectl rollout undo triggered by pipeline on healthz failure. Argo Rollouts automatically aborts and rolls back if AnalysisRun fails (error rate, latency SLO breach).
Audit trail GitHub Actions logs. Git history is the audit trail — every deploy is a commit with author, timestamp, and diff.
Manual approval (prod) GitHub Environment with required reviewers (environment: production). ArgoCD sync policy set to manual for prod app, or Argo Rollouts pause step before full promotion.
Complexity Low — pipeline owns everything, easy to debug. Higher — two systems (pipeline + ArgoCD) must be understood together. But scales better.

How the pipeline would change with ArgoCD + Argo Rollouts

Stage Current With ArgoCD
1–6 Unchanged — scan, build, sign, push to GHCR. Unchanged.
6 (end) Push image to GHCR. Push image to GHCR + open PR / commit to GitOps repo updating image.tag in Helm values or Kustomize overlay.
7 · Dev deploy kubectl set image deployment/... argocd app sync dev-app --wait — ArgoCD applies the new tag from Git.
8 · Staging deploy kubectl set image deployment/... argocd app sync staging-app --wait — Argo Rollouts executes canary strategy declared in the Rollout resource.
9–10 · Smoke + DAST Unchanged — tests against staging URL. Unchanged.
11 · Policy Gate Cosign verify. Cosign verify + optionally check ArgoCD app health status via API.
12 · Prod deploy kubectl set image + manual GitHub approval. GitHub approval gate remains. After approval: argocd app sync prod-app. Argo Rollouts handles blue-green or canary with AnalysisRun (Prometheus metrics gate).
