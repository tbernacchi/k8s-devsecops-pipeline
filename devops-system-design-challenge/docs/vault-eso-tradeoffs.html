HashiCorp Vault + External Secrets Operator (ESO)

When to use it, when to skip it, and what you gain vs what it costs.

When does Vault + ESO make sense?

Scenario Decision Reason
Pods need secrets at runtime (DB passwords, API keys) USE IT GitHub Secrets only exist during CI runs. ESO syncs Vault secrets into Kubernetes Secrets that pods can mount.
Automatic secret rotation USE IT Vault can generate and rotate credentials (DB, cloud IAM, TLS certs) on a TTL. GitHub Secrets are static and manual.
Audit trail — who accessed which secret, when USE IT Vault logs every read/write with full identity context. GitHub has no equivalent secret-access audit log.
Dynamic database credentials USE IT Vault's DB secrets engine generates short-lived, per-app credentials instead of a shared static password.
Multiple clusters / multiple teams sharing secrets USE IT Vault is a single source of truth. Without it, secrets are duplicated across clusters and repos.
Compliance requirements (PCI-DSS, SOC 2, HIPAA) USE IT Vault satisfies encryption-at-rest, access policies, audit logging, and break-glass procedures required by auditors.
Only CI/CD pipeline values (no runtime pod access needed) SKIP IT GitHub Secrets cover this perfectly. Vault adds operational overhead with no benefit if pods never read secrets directly.
Solo project / early-stage startup / home lab SKIP IT Vault requires HA storage backend, unsealing, token renewal, backup strategy — significant ops burden for small teams.
Learning Vault + ESO for interviews / certifications LEARN IT High-value skill in Platform Engineering and DevSecOps roles. Vault + ESO is increasingly asked in senior-level interviews.

Trade-off summary

Dimension GitHub Secrets Vault + ESO
Secret scope CI/CD pipeline only Pipeline + pods at runtime
Rotation Manual Automatic (TTL-based)
Audit log None Full access log in Vault
Dynamic credentials No Yes (DB, PKI, cloud IAM)
Setup complexity Low — GitHub UI / CLI High — Vault HA, ESO, policies, Terraform
Operational burden Near zero Unsealing, token renewal, backup, upgrades
Cost Free Free (OSS) but infra cost for HA
Fine-grained access control Binary (has access or not) Policy per app, per path, per team
Multi-cluster secret sync Manual duplication Native via ESO ClusterSecretStore
Kubernetes Secret created? Only if you create it manually Yes — ESO syncs Vault → K8s Secret automatically

How it works (architecture)

Component Role
HashiCorp Vault Central secret store. Stores, encrypts, and controls access to secrets. Supports dynamic credentials, PKI, and cloud IAM integration.
Terraform Provisions Vault itself (policies, auth methods, secret engines) as code. Makes Vault config reproducible and version-controlled.
External Secrets Operator (ESO) Kubernetes controller. Watches ExternalSecret CRDs, fetches secrets from Vault, and creates/syncs native kubernetes/Secret objects.
ExternalSecret CRD Declarative spec: "fetch this path from Vault and create a K8s Secret named X in namespace Y." Checked into Git — no actual secret value in the repo.
ClusterSecretStore ESO resource that holds the Vault connection config (address, auth method). Reusable across namespaces.
